Документ — единый рабочий план разработки. Статусы отражают состояние кода и проверок в репозитории, а не намерения. После завершения каждого этапа сюда вносятся фактический результат, commit SHA и результаты проверок.

## Принципы ведения плана

- Рабочая ветка текущего цикла: `feat/unified-health-timeline`.
- Стратегические приоритеты и последовательность улучшений описаны в `APP_IMPROVEMENT_ROADMAP.md`; этот документ хранит технические задачи, критерии и журнал.
- `main` — только базовая ветка для сравнения; напрямую не изменять.
- Не считать этап завершённым, пока не выполнены его критерии приёмки и не проверен соответствующий CI.
- После каждого этапа обновлять раздел «Статус этапов и журнал».
- Не перезаписывать более новую реализацию при переносе изменений из старых веток: сначала сравнить историю, затем переносить изменения по смыслу.
- Сохранять данные пользователя; изменения формата хранения выполнять только с миграцией и проверками обратной совместимости.
- Не смешивать данные взрослого и детских профилей. Все профильные ключи должны иметь явную область владения.
- UI, доменную логику, модели, справочники и инфраструктуру разделять по ответственности. Целевой размер исходного файла — до 500 строк, абсолютный предел проекта — 1500 строк.
- Не добавлять клинические выводы, назначения или медицинские нормы без отдельной проверки источников и согласования.

## Текущее состояние проекта

Life Maps — клиентское приложение для карты жизненных событий, личной медицинской истории и семейных профилей. Основное рабочее хранилище пользовательских записей — account-scoped IndexedDB: отдельное пространство на каждый аккаунт и гостевое пространство. Self-hosted серверный аккаунт поддерживает регистрацию/вход, зашифрованный серверный снимок и автоматическую синхронизацию между устройствами. Публичное развёртывание владельцем приложения ещё не выполнено.

В текущей ветке уже присутствуют:
- Карта жизни с пользовательскими событиями.
- Разделы здоровья, семьи и аналитики.
- Отдельные профили детей и профильные ключи медицинских данных.
- Локальное хранение записей, ревизии записей и обмен обновлениями между вкладками.
- Экспорт и импорт резервной копии с проверкой структуры и сериализацией вложений.
- История анализов с несколькими показателями и документом.
- Медицинские события и раздел «На контроле».
- Единый календарь, собирающий события из медицинских записей, контроля, анализов и семейных дат.
- E2E-проверки основных пользовательских сценариев.

### P0 / Этап 4 по запросу. Защита синхронизации и целостность медицинской истории

**Статус: завершён.** Полный CI run [45666744541](https://github.com/TamiArt/health_roadmap/actions/runs/45666744541) прошёл на commit `b6abcf40904c11e2814a4401c87563bae8c7f337`: 82 app unit-теста, 17 server tests, 52/52 Playwright E2E, TypeScript, structure check, npm audit и production build — success. Существующая техническая нумерация календаря и аналитики сохраняется; этот обязательный safety gate добавлен отдельно, чтобы не перенумеровывать ранее согласованные разделы.

Реализовано:
- Персональные версии записей с устойчивым ID: `_version` увеличивается при изменении содержимого, `_updatedAt` хранит время изменения. Поддерживаются медицинские коллекции взрослых/детей и ручные `labMeasurements`.
- Удаления записей хранятся в `syncTombstones` (путь коллекции, ID, версия, время). Tombstone включён в backup, проходит клиентскую и серверную проверку и участвует в merge. Устаревшая запись не может воскреснуть при первом входе; версия выше tombstone сохраняется.
- Каждый push имеет UUID `operationId`, который записывается в `sync-meta` до запроса и повторно используется после сетевого сбоя. Сервер в SQLite-транзакции проверяет ID операции, хеш содержимого и CAS-ревизию.
- `sync_operations` обеспечивает идемпотентность: одинаковый запрос возвращает прежнюю ревизию, тот же ID с другим содержимым отклоняется.
- `change_log` хранит append-only технический журнал; авторизованный `/api/sync/changes?after=<revision>` и последние 20 событий в панели аккаунта показывают историю обновлений без раскрытия медицинских значений.
- Трёхсторонний merge сохраняет независимые изменения, конфликт одного поля требует выбора local/server; конфликтные и pending-метаданные остаются в IndexedDB до успешного завершения.
- Добавлены тесты для повторной операции, повторного использования ID с иным payload, журнала, tombstone при первом входе и сохранения более новой версии.
- Анализы получили графики динамики по показателям/одинаковым единицам; ручные значения из каталога тоже отображают динамику. Для построения тренда нужны минимум два числовых результата.
- Поиск анализов расширен по названию, показателям, значениям, единицам, датам и прикреплённым документам; доступен фильтр диапазона дат.
