# Финальный чек-лист MVP Life Maps

Этот документ разделяет автоматические проверки, которые выполняются в репозитории, и эксплуатационные проверки, которые требуют реального сервера и нескольких физических устройств. Нельзя отмечать ручной gate пройденным только на основании unit/E2E теста.

## Автоматические проверки в CI

CI workflow `.github/workflows/ci.yml` должен успешно выполнить все шаги на одном и том же HEAD feature-ветки:

- [ ] `npm ci --no-audit --no-fund`
- [ ] `npm run typecheck`
- [ ] `npm run check:structure`
- [ ] `npm audit --audit-level=high`
- [ ] `npm test` (Vitest, API/server tests и backup/restore tests)
- [ ] Установка Chromium через Playwright
- [ ] `npm run test:e2e`
- [ ] `npm run build`

E2E покрывает основные разделы, формы медицинской истории, семейные профили, мобильные размеры, PWA shell и офлайн-оболочку. Release E2E дополнительно проверяет регистрацию, вход в том же аккаунте на втором browser context, доставку изменений, офлайн-очередь и распространение удаления.

## Обязательные ручные release gates

- [ ] Развернуть production по HTTPS на домене владельца; проверить `/api/health` и `/api/ready`.
- [ ] Создать тестовый аккаунт, выйти и войти повторно; проверить отказ неверного пароля и повторной регистрации.
- [ ] Войти в один аккаунт на двух независимых устройствах/браузерах и убедиться, что данные появляются на обоих.
- [ ] Отключить сеть на устройстве A, добавить/изменить/удалить запись; убедиться, что запись остаётся локально и отображается pending/offline.
- [ ] Восстановить сеть и убедиться, что очередь синхронизировалась без дубликатов и потери вложений.
- [ ] Одновременно изменить одно поле на двух устройствах; убедиться, что возникает явный конфликт и выбранная стратегия не удаляет независимые изменения.
- [ ] Удалить запись на одном устройстве и убедиться, что tombstone распространяется, а удалённая запись не воскресает на другом.
- [ ] Проверить взрослые и детские профили: анализы, документы, вакцинацию, стоматологию, медицинские события, контрольные показатели, историю, календарь и аналитику.
- [ ] Экспортировать данные с документами, импортировать копию в отдельное тестовое пространство и сравнить записи, даты, значения, единицы и вложения.
- [ ] Выполнить серверный backup, проверить manifest/checksum/integrity, восстановить копию на отдельной тестовой БД и сверить количество записей.
- [ ] Проверить интерфейс на реальных Android/iOS устройствах, установить PWA, пройти основные формы и проверить поведение после перезапуска браузера.
- [ ] Выполнить ручной keyboard/screen-reader и диалоговый аудит.
- [ ] Настроить offsite backup и проверить, что ключ шифрования хранится отдельно от резервных копий.

## Критерии выпуска

MVP можно объявить готовым к ограниченному использованию после успешного CI и закрытия ручных gates, относящихся к фактически включённым в production функциям. Пока production сервер, независимые устройства и offsite restore drill не проверены, статус — **release candidate**, а не подтверждённый production go-live.

Перед использованием для реальной медицинской истории владелец сервера должен проверить обновления ОС/контейнеров, права доступа, мониторинг, политику хранения резервных копий и порядок реагирования на инциденты.
