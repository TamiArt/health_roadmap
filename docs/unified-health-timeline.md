# Единая хронология здоровья — этап 3

## Назначение

Хронология — производное представление сохранённых данных, а не новое хранилище. Каждая строка показывает одно событие, указывает профиль и точный исходный ключ/идентификатор записи. Изменение и удаление выполняются в исходном разделе.

## Контракт события

- `id` — стабильный идентификатор элемента ленты.
- `source.key` + `source.recordId` — однозначная ссылка на сохранённую запись; `source.section` определяет исходный раздел.
- `profileId` / `profileLabel` — контекст владельца записи.
- `kind` — категория для фильтра.
- `date`, `dateLabel`, `datePrecision`, `sortDate`, `dateEnd` — исходная дата, человекочитаемая подпись, точность и границы известного периода.
- `title`, `details`, `searchable` — представление и поисковый индекс.

## Источники

| Источник | Категория | Правило отображения | Переход |
|---|---|---|---|
| `labResultEntries` | Анализы | Одна строка на исследование; все показатели, заметки и документы остаются в карточке | Вкладка анализов, якорь исследования |
| `labMeasurements` | Ручные измерения | Отдельная строка на измерение | Каталог анализов, якорь измерения |
| `labUploads` | Документы | Отдельная строка на файл из каталога анализов | Каталог анализов, якорь файла |
| `healthEvents` | Медицинские события | Отдельная строка на событие | Вкладка событий, якорь записи |
| `vaccineRecords` | Вакцинация | Отдельная строка на факт введения вакцины | Вкладка вакцинации, якорь записи |
| `adultToothData` / `childHealth:<id>:toothData` | Стоматология | Отдельная строка на зуб; без даты, если она не хранится в модели | Стоматологическая карта, выбранный зуб |
| `healthMonitoring` | Контроль показателей | Отдельная строка на каждое измерение; источник ссылается на родительский пункт и конкретное измерение | Вкладка контроля, якорь измерения |
| `familyEvents` | Семейная история | Одна строка на семейную дату; хранится глобально, не копируется в детские профили | Раздел семьи, якорь памятной даты |

## Дедупликация

- Дедупликация выполняется по паре ключа хранилища и ID исходной записи.
- Показатели и документы одного лабораторного исследования агрегируются в одну строку исследования, а не превращаются в несколько событий.
- Факты измерений мониторинга остаются отдельными событиями; идентификатор исходной записи включает ID пункта контроля и ID измерения.
- Ручное измерение, файл из каталога и подробное лабораторное исследование не объединяются эвристически по совпадению названия или даты: это разные сохранённые записи. Так исключается ошибочное слияние похожих, но не тождественных данных.

## Даты и сортировка

- Поддерживаются точные ISO-даты, даты `ДД.ММ.ГГГГ`, месяц `ММ.ГГГГ`, год `ГГГГ` и сезон с годом (`Весна 2024`, `Лето 2024` и т. п.).
- Для месяца, года и сезона сохраняется исходная точность; дата не выдаётся за точный день.
- Фильтр периода учитывает пересечение диапазона пользователя с полным известным периодом записи.
- Невалидные и неизвестные даты остаются видимыми с исходной подписью и сортируются после датированных событий.
- При одинаковых датах используется стабильная сортировка по ID; направление «новые/старые» не меняет порядок равных дат.
- Старые записи не отбрасываются из-за возраста.

## Профили и переходы

- Взрослые и детские источники собираются с исходными ключами, включая префикс `childHealth:<id>:`.
- Фильтр профиля поддерживает все профили, взрослый профиль и каждый существующий профиль ребёнка.
- Каждая строка отображает подпись профиля.
- Переход открывает нужный раздел и прокручивает к DOM-якорю исходной записи; для детской записи дополнительно открывается нужный профиль ребёнка.
- Удаление или изменение записи в исходном разделе автоматически отражается в хронологии после обновления данных.

## Проверки

- Unit: сбор всех источников, профильная фильтрация, точная идентичность источника, группировка показателей, отдельные измерения, частичные/невалидные даты, пересечение диапазонов, одинаковые даты, старые записи и 1000 элементов.
- E2E: поиск/категория/диапазон/сортировка, переход к взрослой записи, фильтрация по детскому профилю и переход к исходной записи ребёнка.
- Полная приёмка этапа — typecheck, structure check, dependency audit, unit, E2E и production build на одном commit.

## Совместимость и сохранность

Новые записи и миграции не создаются. Хронология строится из существующих ключей IndexedDB, поэтому backup schema не меняется, а исходные записи и вложения не копируются и не перезаписываются.
