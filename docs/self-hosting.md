# Развёртывание Life Maps на собственном сервере

Этот вариант не использует платные облачные базы данных или сервисы авторизации. Приложение, API и SQLite запускаются на вашем сервере в Docker Compose; Caddy автоматически получает и обновляет TLS-сертификат для домена.

## Что реализовано

- Регистрация и вход по email и паролю (пароль от 12 символов).
- Пароли хранятся не в открытом виде: используется scrypt с уникальной солью.
- Сессии хранятся на сервере; браузер получает HttpOnly, SameSite=Strict cookie. В production cookie помечена Secure.
- Данные каждого аккаунта хранятся отдельно. Серверная резервная копия шифруется AES-256-GCM перед записью в SQLite.
- В резервную копию попадают все поддерживаемые приложением записи и вложения, включая Blob-файлы, семейные и детские профили.
- После входа на новом устройстве данные аккаунта автоматически загружаются в отдельное локальное пространство. Изменения отправляются на сервер автоматически; обновления других устройств обнаруживаются фоновым опросом ревизии.
- Для защиты от случайной перезаписи используется номер ревизии. Устаревшая запись получает HTTP 409, а не заменяет более свежую.
- Локальный экспорт/импорт JSON остаётся доступным независимо от аккаунта.

Синхронизация выполняется автоматически. Локальные изменения ставятся в устойчивую очередь, отправляются после восстановления сети и повторяются с backoff. При одновременном редактировании одного поля синхронизация не перезаписывает данные автоматически: пользователь выбирает, какую версию конфликтующих полей оставить; остальные независимые изменения объединяются.

## Требования к серверу

- Linux VPS или собственный сервер с публичным IP.
- Docker Engine и Docker Compose plugin.
- Доменное имя, DNS A/AAAA-запись которого указывает на сервер.
- Открытые входящие порты TCP 80 и 443 (для HTTPS через Caddy).

Само приложение и все его серверные компоненты бесплатны и с открытым исходным кодом. Стоимость VPS и домена зависит от выбранного поставщика; бесплатный публичный хостинг этим проектом не предоставляется.

## Запуск

В корне репозитория:

~~~bash
cp .env.example .env
~~~

Сгенерируйте ключ шифрования:

~~~bash
openssl rand -hex 32
~~~

Внесите в .env:

- DATA_ENCRYPTION_KEY — сгенерированные 64 hex-символа.
- DOMAIN — ваш домен без https://.
- NODE_ENV=production.

Затем задайте права на env-файл и запустите:

~~~bash
chmod 600 .env
docker compose up -d --build
docker compose ps
docker compose logs -f app backup caddy
~~~

После запуска откройте https://ваш-домен. Caddy автоматически запросит и будет обновлять TLS-сертификат. Liveness: https://ваш-домен/api/health; readiness с проверкой SQLite и ключа шифрования: https://ваш-домен/api/ready. Порты API напрямую наружу не публикуются.

## Локальная разработка

Скопируйте .env.example в .env, задайте ключ шифрования и установите NODE_ENV=development. В одном терминале:

~~~bash
npm ci
npm run dev:server
~~~

Во втором терминале:

~~~bash
npm run dev
~~~

Vite проксирует /api на локальный API-сервер 127.0.0.1:3000.

## Резервное копирование и восстановление сервера

Отдельный backup-контейнер автоматически создаёт SQLite-снимок при старте и затем каждые 24 часа. Выполняются WAL checkpoint, проверка схемы, `PRAGMA integrity_check`, SHA-256 и создание manifest. По умолчанию хранятся 14 дней; срок и интервал можно изменить через `BACKUP_RETENTION_DAYS` и `BACKUP_INTERVAL_HOURS`.

Ручной снимок: `docker compose run --rm --no-deps backup node scripts/backup.mjs`.

Для восстановления остановите `app` и `backup`, затем выполните `docker compose run --rm --no-deps backup node scripts/restore.mjs /backups/ИМЯ_КОПИИ.sqlite --confirm` и снова запустите сервисы. Скрипт проверяет checksum и SQLite integrity, а перед заменой создаёт safety-копию текущей базы в `/backups/pre-restore`.

Постоянные volumes: `life_maps_data` (SQLite), `life_maps_backups` (снимки), `caddy_data` и `caddy_config` (TLS-состояние). Не используйте `docker compose down -v` при обычном обновлении.

Backup volume на том же VPS не защищает от потери всего сервера: настройте отдельное offsite-копирование по [эксплуатационной инструкции](./operations-runbook.md). Два критичных элемента восстановления: SQLite-файл и исходное значение `DATA_ENCRYPTION_KEY`. Ключ храните отдельно, с правами `.env` 0600; без него расшифровать серверные копии невозможно. Не помещайте `.env`, ключ или содержимое базы в Git, публичные issue и чаты.

## Текущие ограничения

- Подтверждение владения email и сброс забытого пароля пока не реализованы: для них требуется SMTP-сервер и отдельный процесс восстановления. Регистрация создаёт аккаунт сразу, без письма подтверждения.
- Синхронизация выполняется, пока приложение открыто; после закрытия браузера JavaScript не выполняется в фоне. Неотправленные изменения остаются в локальной очереди и отправляются при следующем открытии приложения или восстановлении соединения.
- Если два устройства одновременно изменили одно и то же поле записи, конфликт требует явного выбора версии в интерфейсе. Система автоматически сохраняет все независимые изменения и не допускает незаметную перезапись конфликтующих данных.
- Сессии действуют 30 дней. Отзыв всех сессий и управление устройствами пока не вынесены в интерфейс.
- Лимит тела API-запроса — 105 МБ; лимит локальной резервной копии приложения — 100 МБ.
- Для медицинских и иных чувствительных данных используйте собственный сервер с обновляемой ОС, ограниченным доступом, HTTPS и регулярными резервными копиями. Шифрование пользовательских снимков защищает их содержимое в SQLite, но не защищает устройство сервера от компрометации во время работы приложения.
- Встроенный backup worker хранит копии на том же VPS; offsite-копирование и внешние уведомления о сбоях необходимо настроить владельцу сервера.
- Приложение рассчитано на один API экземпляр с SQLite; несколько реплик с общим volume не поддерживаются.

## API

- POST /api/auth/register — регистрация.
- POST /api/auth/login — вход.
- POST /api/auth/logout — выход.
- GET /api/auth/me — текущая сессия.
- GET /api/data — полный зашифрованный на сервере снимок аккаунта и его ревизия.
- GET /api/sync/status — лёгкая проверка текущей ревизии и времени последнего обновления без передачи содержимого медицинских записей.
- PUT /api/data — создание или обновление резервной копии с обязательной ожидаемой ревизией.
- GET /api/health — liveness процесса.
- GET /api/ready — readiness базы и ключа шифрования.


Эксплуатационные процедуры, команды проверки, offsite-копирование и аварийное восстановление: [docs/operations-runbook.md](./operations-runbook.md).
