# Защита синхронизации и история изменений

## Модель данных

Медицинские коллекции, которые хранят записи с устойчивым `id`, получают метаданные записи при локальном сохранении:
- `_version` — монотонная версия конкретной записи в пределах её локальной коллекции;
- `_updatedAt` — время последнего изменения записи.

При удалении запись не исчезает бесследно из протокола синхронизации. В резервную копию включается служебный ключ `syncTombstones`: для пути коллекции и ID удалённой записи сохраняются версия и время удаления. Tombstone не содержит медицинское содержимое.

## Слияние

Снимки объединяются трёхсторонним merge относительно последней общей базовой версии:
- независимые изменения объединяются;
- одновременное изменение одного поля остаётся конфликтом;
- конфликт не разрешается автоматически в пользу локальной или серверной копии;
- tombstone применяется после объединения снимков: запись с версией не выше версии удаления не восстанавливается;
- более новая версия записи сохраняется, даже если пришёл более старый tombstone;
- tombstone профиля ребёнка удаляет связанные ключи `childHealth:<id>:` из итогового снимка.

При первом входе на устройстве с уже заполненной локальной базой локальные данные не заменяются серверным снимком. Они объединяются с сервером; при конфликте оба варианта остаются в метаданных конфликта до явного выбора пользователя.

## Идемпотентность и журнал

Каждая отправка снимка имеет UUID `operationId`. Клиент сохраняет его в durable sync metadata до сетевого запроса и повторно использует при сетевой ошибке. Сервер хранит пару (account, operationId), хеш содержимого записей и присвоенную ревизию:
- повтор той же операции возвращает исходную ревизию и не создаёт новую запись журнала;
- повторное использование ID с другим содержимым отклоняется;
- сравнение `expectedRevision` и запись снимка/операции/журнала выполняются в одной SQLite-транзакции.

Таблица `change_log` — append-only журнал ревизий аккаунта. Она хранит только технические метаданные (ревизия, ID операции, время, количество элементов и хеш), а не медицинские значения или документы. Авторизованный endpoint `GET /api/sync/changes?after=<revision>` возвращает до 100 событий. В панели аккаунта отображаются последние 20 синхронизаций.

## Восстановление и ограничения

Локальная очередь хранится в IndexedDB и повторяется после reconnect или следующего запуска приложения. Пока приложение закрыто, браузер не исполняет обычный JavaScript polling; фоновая доставка без открытого приложения не обещается.

Журнал хранит ревизии снимков, а не полную копию каждого медицинского значения. Для восстановления данных используются зашифрованный актуальный снимок, локальный экспорт и явное разрешение конфликтов. Серверный CAS остаётся последним барьером от перезаписи более новой ревизии.

## Проверки

Unit/API/E2E регрессии должны подтверждать:
- повторный запрос с тем же operationId не увеличивает ревизию;
- один operationId нельзя использовать для другого содержимого;
- журнал доступен только авторизованному аккаунту и не содержит медицинских значений;
- tombstone удаляет устаревшую локальную копию при первом входе;
- запись с версией выше tombstone не удаляется;
- конкурентные изменения одного поля не перезаписываются без выбора;
- некорректный backup не изменяет локальные данные и серверную ревизию.
