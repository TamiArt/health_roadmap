# Модель пользовательских данных Life Maps

## Архитектура и единый доступ к данным

- Единственная точка доступа приложения к пользовательскому хранилищу — `src/app/storage.ts`.
- Компоненты используют `usePersistentState`; прямые операции с IndexedDB из UI-компонентов запрещены.
- Доменные модели и проверки находятся в профильных модулях (`models.ts`, `healthRecords.ts`, `medicalHistoryModel.ts`).
- Справочники и демонстрационные данные не являются пользовательскими записями и не должны записываться поверх пользовательских данных.
- Источник истины для активного пользователя — его локальное пространство IndexedDB. Данные разных аккаунтов в одном браузерном профиле разделены префиксом `accountId::`; незарегистрированное пространство использует префикс `guest::`. Сервер хранит отдельный зашифрованный снимок каждого аккаунта, который автоматически синхронизируется между устройствами.
- Каждая физическая запись IndexedDB имеет форму `{ key: "<scope>::<logicalKey>", value, revision }`. Ревизия защищает от записи устаревшим экземпляром вкладки. `usePersistentState` работает с логическим ключом и автоматически добавляет текущий scope.
- Удалённые ключи сохраняются как tombstone-записи с увеличенной ревизией, чтобы устаревшая вкладка не восстановила удалённые данные.

## Хранилище

| Параметр | Значение |
|---|---|
| IndexedDB database | `life-maps` |
| Object store | `app-records` |
| Key path | `key` |
| IndexedDB version | `1` |
| Backup format | `life-maps-backup` |
| Backup schema | `1` |
| Максимальный JSON backup | 100 МБ |
| Максимальный файл результата | 15 МБ |

`app-records` содержит пользовательские разделы; `sync-meta` хранит состояние синхронизации аккаунта (серверную ревизию, время последней синхронизации, базовый снимок и устойчивый признак ожидающей отправки). Миграция IndexedDB v1 → v2 транзакционно переносит старые неразмеченные записи в гостевое пространство `guest::` без удаления данных. Аккаунтный gate проверяет сессию до отображения медицинских записей; выход переключает приложение на гостевое пространство, а записи аккаунта остаются в его namespace.

## Разрешённые ключи

| Ключ | Назначение |
|---|---|
| `lifeEvents` | События карты жизни |
| `familyMembers` | Взрослые члены семьи |
| `children` | Профили детей |
| `familyEvents` | Семейные даты |
| `vaccineStatuses` | Статусы вакцинации основного профиля |
| `vaccineRecords` | Датированная история вакцинации основного профиля |
| `adultToothData` | Стоматологические данные основного профиля |
| `labUploads` | Загруженные файлы анализов основного профиля |
| `labMeasurements` | Ручные значения анализов основного профиля |
| `healthEvents` | Медицинские события основного профиля |
| `healthMonitoring` | Контрольные показатели основного профиля |
| `labResultEntries` | Подробные результаты анализов основного профиля |
| `notificationSettings` | Настройки уведомлений |
| `childHealth:{childId}:{type}` | Изолированные медицинские данные ребёнка |

Для дочернего профиля разрешены только типы: `vaccineStatuses`, `vaccineRecords`, `toothData`, `labUploads`, `labMeasurements`, `healthEvents`, `healthMonitoring`, `labResultEntries`. Идентификатор профиля должен соответствовать `[a-zA-Z0-9_-]+` и существовать в записи `children`. Ключи проверяются allowlist-ом на клиенте и сервере.

## Идентификаторы и даты

- Пользовательские записи имеют стабильный непустой `id`; внутри одной коллекции идентификаторы уникальны.
- Вложенные показатели и документы имеют собственные уникальные ID.
- ID создаётся через `crypto.randomUUID()`; резервный генератор включает timestamp, счётчик и случайную часть, чтобы снизить риск коллизий в разных вкладках и браузерах.
- Для медицинских событий, результатов анализов, вакцинаций, измерений и датированных измерений мониторинга используется календарно проверенная дата `YYYY-MM-DD`. В исторических записях мониторинга необязательные поля следующей/последней даты и напоминания сохраняются совместимо: если поле задано, оно проверяется.
- Семейные памятные даты могут хранить неполную точность (день, месяц, сезон, год или неизвестная дата); нормализация отображения выполняется в `medicalHistoryModel.ts` без изменения исходного значения.
- Взрослые и детские записи хранятся под разными ключами; детская запись всегда ссылается на существующий профиль.

## CRUD, конкурентный доступ и удаление

- `writeRecord` выполняет compare-and-write по ревизии; устаревшая вкладка получает конфликт вместо перезаписи.
- Обновления между вкладками передаются через `BroadcastChannel`; уведомления с устаревшими ревизиями игнорируются.
- Удаление профиля ребёнка и его записей выполняется одной read-write транзакцией.
- Удаление/восстановление раздела повышает ревизии затронутых ключей.
- Импорт резервной копии сначала проверяет весь документ и вложения, затем одной транзакцией заменяет снимок. Отклонённый импорт не должен изменять действующую базу.
- Перед заменой локального набора данных интерфейс требует явного подтверждения.

## Экспорт, импорт и миграции

JSON backup включает формат, версию схемы, дату экспорта и все разрешённые логические ключи только активного пространства. Импорт меняет только активный namespace и не затрагивает локальные данные других аккаунтов. Blob-вложения сериализуются как Base64 с MIME-типом и восстанавливаются в Blob. Проверки выполняются до транзакции записи: формат, версия, allowlist, структура записей, календарные даты, уникальность ID, связи профилей, глубина вложенности и целостность Base64.

- Backup schema 0 мигрируется в schema 1 с сохранением поддерживаемых записей и вложений.\n- IndexedDB schema 1 мигрируется в schema 2; старые ключи переходят в `guest::`.
- Неизвестные ключи и версии новее текущей отклоняются; они не удаляются молча.
- Сервер повторно проверяет резервную копию до шифрования и записи.
- Миграции IndexedDB и миграции JSON backup — разные механизмы; изменение одного не должно неявно менять другое.

## Серверный аккаунт и границы безопасности

- Сервер хранит отдельную AES-256-GCM зашифрованную резервную копию для каждого аккаунта.
- **Известное ограничение:** локальная IndexedDB пока одна на профиль браузера и не разделена по `accountId`. Серверные резервные копии изолированы, но два разных аккаунта, поочерёдно открытые в одном профиле браузера, используют одно локальное рабочее пространство. До реализации account-scoped IndexedDB или безопасного переключения локальных пространств один профиль браузера следует использовать для одного пользователя приложения; выход из аккаунта сам по себе не удаляет локальные записи.
- API проверяет принадлежность резервной копии текущей сессии и контролирует ревизии; `/api/sync/status` отдаёт только ревизию и время обновления без передачи медицинского payload.
- Автоматическая синхронизация использует полные проверенные снимки с compare-and-swap по серверной ревизии. Изменение локальной записи ставит устойчивый `pending`-флаг в `sync-meta`; изменения объединяются с базовым снимком и серверной версией по ID записей/вложенных объектов.\n- Независимые изменения объединяются автоматически, удаления распространяются как различия относительно базового снимка. Одновременное изменение одного поля не выбирает победителя молча: интерфейс показывает конфликт и предлагает явно оставить значения устройства или сервера, сохраняя не конфликтующие изменения.\n- При отсутствии сети локальные записи и pending-флаг сохраняются в IndexedDB; повтор отправки выполняется по событию `online`, с экспоненциальным backoff и при следующем открытии приложения. Пока приложение открыто, другие устройства опрашиваются через лёгкий `/api/sync/status` каждые 5 секунд; полный backup скачивается только при изменении ревизии или локальной очереди.
- IndexedDB браузера не зашифрована приложением; защита зависит от устройства и профиля браузера.
- Экспортированный JSON содержит медицинские и семейные сведения в читаемом виде. Его следует хранить в защищённом месте.
- Удаление данных сайта удаляет локальную базу. Нужна независимая резервная копия.
