# Модель пользовательских данных Life Maps

## Принципы

- Источник пользовательских данных — локальная IndexedDB текущего профиля браузера.
- Данные принадлежат пользователю и не отправляются на сервер.
- UI получает типизированные значения через `usePersistentState`; React state выступает рабочей копией для редактирования.
- Справочные данные каталога и демонстрационные значения не смешиваются с пользовательскими записями.
- Импорт резервной копии заменяет локальный набор записей атомарной транзакцией.

## Хранилище

- Database: `life-maps`
- Object store: `app-records`
- Object-store keyPath: `key`
- IndexedDB database version: 1
- Backup format: `life-maps-backup`
- Backup schema version: 1

Каждая запись имеет форму `{ key, value }`. Вложенные записи не разбиваются на отдельные таблицы: для текущего небольшого клиентского приложения это упрощает транзакционное сохранение целого пользовательского раздела.

## Ключи и данные

| Ключ | Значение |
|---|---|
| `lifeEvents` | Массив событий карты жизни |
| `familyMembers` | Массив взрослых членов семьи |
| `children` | Массив профилей детей |
| `familyEvents` | Массив семейных дат |
| `vaccineStatuses` | Словарь статусов вакцинации основного профиля |
| `adultToothData` | Словарь стоматологических статусов и заметок основного профиля |
| `labUploads` | Файлы результатов анализов основного профиля, хранятся как Blob |
| `childHealth:{childId}:vaccineStatuses` | Статусы вакцинации отдельного ребёнка |
| `childHealth:{childId}:toothData` | Стоматологические записи отдельного ребёнка |
| `childHealth:{childId}:labUploads` | Файлы анализов отдельного ребёнка |

Ключи проверяются allowlist-ом. Для child-specific записей разрешены только перечисленные суффиксы.

## Каталог лабораторных исследований

- `LabTestConcept` описывает сущность исследования и имеет стабильный `conceptId`.
- `LabTestAssignment` связывает концепт с возрастным этапом и частотой.
- `LAB_TEST_CONCEPTS` и `LAB_TEST_ASSIGNMENTS` сейчас являются нормализованными read-model коллекциями.
- `LIFE_STAGES` остаётся совместимым группированным представлением для UI. Перевод его на полностью нормализованный источник — отдельный следующий рефакторинг.
- Повторение исследования в разных возрастах не означает дубль: это разные назначения одного концепта.

## Резервная копия

JSON-файл содержит формат, версию схемы, дату экспорта и объект записей. Blob-вложения кодируются в base64 с MIME-типом, затем восстанавливаются в Blob при импорте.

- Максимальный размер backup: 100 МБ.
- Максимальный размер одного загружаемого результата: 15 МБ.
- Импорт проверяет формат, версию, allowlist ключей и базовую форму записей.
- Восстановление выполняется одной read-write транзакцией: старые записи очищаются и новые записываются в рамках той же транзакции.
- Импорт требует явного подтверждения в UI.

## Миграции

Backup schema version 0 преобразуется в version 1 без изменения допустимых записей. Новые изменения формата должны добавлять отдельную миграцию для каждой версии и unit-тесты на исходную/целевую форму.

Изменение схемы самой IndexedDB требует увеличения `DB_VERSION` и миграции в `onupgradeneeded`. Не удалять object stores или записи без сценария обратимого переноса.

## Ограничения и безопасность

- IndexedDB не зашифрована приложением; защита зависит от учётной записи и безопасности устройства/браузера.
- JSON backup содержит медицинские и семейные данные в читаемом виде. Хранить его нужно отдельно и защищённо.
- Синхронизация между устройствами, серверная БД, аккаунты и совместный доступ отсутствуют.
- Очистка данных сайта удаляет локальную базу; для защиты от потери устройства нужны независимые резервные копии.
- Старые изменения, существовавшие только в React state до внедрения IndexedDB, автоматически не мигрируются после перезагрузки страницы.
