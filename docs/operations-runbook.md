# Эксплуатация и аварийное восстановление Life Maps

## Первый запуск

1. Подготовьте Linux VPS/сервер с Docker Engine и Docker Compose plugin.
2. Направьте DNS A/AAAA домена на публичный IP сервера. Откройте входящие TCP 80/443; SSH ограничьте доверенными IP.
3. В каталоге проекта создайте приватный env-файл:

```bash
umask 077
cp .env.example .env
openssl rand -hex 32
chmod 600 .env
```

4. Впишите домен и сгенерированный 64-символьный `DATA_ENCRYPTION_KEY` в `.env`. Не вставляйте ключ в команды, shell history, CI-логи, issue или чат.
5. Запустите:

```bash
docker compose up -d --build
docker compose ps
docker compose logs --tail=100 app backup caddy
```

Caddy получает и обновляет TLS-сертификат автоматически. Приложение и backup worker не публикуют порты наружу; наружу доступны только 80/443 Caddy.

## Постоянное хранение

- Основная SQLite база: Docker volume `life_maps_data`, путь внутри app-контейнера `/app/data/life-maps.sqlite`.
- Резервные копии: отдельный volume `life_maps_backups`, путь `/backups`.
- TLS-сертификаты и состояние Caddy: volumes `caddy_data` и `caddy_config`.

Не удаляйте эти volumes при обновлении контейнеров. Команда `docker compose down -v` удаляет постоянные данные и резервные копии и не должна использоваться для обычного обновления.

## Автоматические резервные копии

Отдельный изолированный backup-контейнер создаёт SQLite snapshot через `VACUUM INTO` сразу после готовности базы и далее каждые 24 часа. Для каждого снимка выполняются:

- WAL checkpoint перед копированием;
- проверка схемы базы и `PRAGMA integrity_check`;
- вычисление SHA-256;
- создание manifest с именем, временем, контрольной суммой и результатом integrity check;
- права доступа 0600;
- автоматическое удаление копий старше срока хранения.

По умолчанию сохраняются 14 дней. Параметры: `BACKUP_INTERVAL_HOURS` (1–168) и `BACKUP_RETENTION_DAYS` (1–365) в `.env`. Ошибки не скрываются: worker пишет структурированное событие в stdout/stderr и повторяет попытку через 5 минут.

Создать копию вручную:

```bash
docker compose run --rm --no-deps backup node scripts/backup.mjs
```

Посмотреть результаты:

```bash
docker compose logs --since=48h backup
```

### Копия вне VPS

Docker volume защищает от потери/перезапуска контейнера, но не от потери самого сервера или диска. Регулярно копируйте каталог `/backups` на отдельное физическое устройство или независимое хранилище:

```bash
mkdir -p ./offsite-backups
docker compose run --rm --no-deps \
  -v "$PWD/offsite-backups:/offsite" --entrypoint sh backup \
  -c 'umask 077 && cp -a /backups/. /offsite/'
```

Файлы резервной копии содержат хэши учётных записей и зашифрованные пользовательские снимки; всё равно обращайтесь с ними как с конфиденциальными данными. Ключ `DATA_ENCRYPTION_KEY` храните отдельно от копий базы, в защищённом менеджере секретов/офлайн-копии. Не кладите ключ рядом с резервной копией в тот же архив.

## Проверяемое восстановление

Проверка целостности выполняется при создании копии и повторно перед восстановлением. Процедура восстановления требует остановить оба процесса, использующих SQLite:

```bash
docker compose stop app backup
docker compose run --rm --no-deps backup \
  node scripts/restore.mjs /backups/ИМЯ_КОПИИ.sqlite --confirm
docker compose up -d app backup caddy
```

Скрипт проверяет manifest и SHA-256, запускает SQLite integrity check, перед заменой текущей базы создаёт отдельную safety-копию в `/backups/pre-restore`, устанавливает проверенный снимок и повторно проверяет его. Не запускайте восстановление при работающем app-контейнере: SQLite-файл должен быть закрыт всеми процессами.

Автоматизированные тесты проверяют создание консистентного снимка, контрольную сумму, отказ от изменённого файла и восстановление с предварительной safety-копией. Перед реальным вводом данных выполните пробное восстановление на отдельном тестовом сервере/копии volumes. Это не заменяет периодическую практическую проверку вне production.

## Секреты и шифрование

- `DATA_ENCRYPTION_KEY` — 32 случайных байта в hex; сервер проверяет длину и формат при старте.
- Пароли хэшируются scrypt с индивидуальной солью; session token случаен, в SQLite хранится только его SHA-256.
- Серверные пользовательские снимки шифруются AES-256-GCM с уникальным IV и authentication tag.
- `.env` исключён из Git и должен иметь права 0600. Не передавайте переменную ключа backup-контейнеру: ему не требуется расшифровывать данные.
- Потеря ключа означает невозможность расшифровать резервные копии аккаунтов. Не генерируйте новый ключ при обновлении контейнера.
- Ротация ключа шифрования не автоматизирована; до её отдельной реализации сохраняйте исходный ключ и все зашифрованные копии.

## HTTPS и сетевой периметр

Caddy обслуживает домен, автоматически получает и обновляет TLS-сертификаты и проксирует запросы к внутреннему app-сервису. В конфигурации заданы HSTS, запрет MIME sniffing, frame denial, политика referrer и ограничение browser capabilities. Порт 3000 наружу не публикуется. Не запускайте API напрямую на публичном интерфейсе без reverse proxy и TLS.

## Мониторинг и диагностика

- `GET /api/health` — liveness процесса.
- `GET /api/ready` — readiness: проверяет SQLite и наличие 256-битного ключа; при неисправности возвращает HTTP 503.
- Docker healthcheck опрашивает readiness каждые 30 секунд и помечает нездоровый контейнер.
- HTTP-запросы и ошибки сервера выводятся в JSON-лог без email, содержимого запросов, cookie и медицинских значений. Для корреляции ответа возвращается `X-Request-Id`.
- Docker log rotation ограничен по размеру и количеству файлов.

Команды для проверки:

```bash
docker compose ps
curl -fsS https://ВАШ-ДОМЕН/api/health
curl -fsS https://ВАШ-ДОМЕН/api/ready
docker compose logs --since=1h app backup caddy
```

Подключите внешний uptime monitor к `/api/ready` и настройте оповещение при HTTP != 200 или отсутствии успешного события `backup_created` дольше одного интервала. Секреты и медицинские данные не включайте в мониторинговые метки.

## Границы текущей конфигурации

- Backup volumes размещены на том же сервере; независимая offsite-копия должна настраиваться владельцем сервера отдельно.
- Для резервных копий нет встроенной отправки email/SMS-оповещений; контроль выполняется по Docker logs или внешним uptime/log мониторингом.
- Приложение рассчитано на один экземпляр API с SQLite. Не запускайте несколько app-реплик с общим SQLite volume; rate limiter пока локален процессу.
- Подтверждение email и сброс пароля требуют SMTP и отдельной реализации.
- Для реальных медицинских данных владелец сервера отвечает за обновления ОС/Docker, SSH-доступ, firewall, физическую безопасность дисков и соблюдение применимых требований к обработке персональных/медицинских данных.
